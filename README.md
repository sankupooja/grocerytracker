

# Technical Documentation: Adaptive Meal & Grocery Planner

## Architectural Overview
This application is designed as a **Multi-Phase, Inventory-driven State Machine**. Instead of generating static, unchangeable menus, the system separates planning and execution into three states:
1.  **Phase 1 (Budget Planning):** The LLM acts as an economic assistant, proposing a grocery inventory that strictly fits within a user's target weekly budget.
2.  **Phase 2 (State Tracking):** The user acts as the real-world filter, selecting what they *actually* bought. The application dynamically monitors total cart value in real time against the budget ceiling.
3.  **Phase 3 (Constrained Execution):** The LLM acts as a creative chef, constructing a 7-day meal plan limited *strictly* to the inventory items marked as bought in Phase 2.

## 1. Database Module (`database.py`)
This file coordinates the SQLite data persistence layer. Because Streamlit applications rerun from top to bottom on every user interaction, this module maintains state integrity.

### Connection & Initialization
*   `get_connection()`
    *   **Purpose:** Establishes a local thread-safe connection to `meal_planner.db`.
    *   **Behavior:** Sets `sqlite3.Row` as the row factory, allowing database queries to be parsed dynamically as Python dictionaries.
*   `init_db()`
    *   **Purpose:** Bootstraps the application. Creates four core tables if they do not already exist: `user_profile`, `meals`, `grocery_list`, and `deviations`. It also inserts a default profile row if the application is starting for the first time.

### Profile CRUD Helpers
*   `get_user_profile()`
    *   **Purpose:** Retrieves the current active user's metrics (diet, allergies, calorie targets, and budget limit).
*   `update_user_profile(dietary_type, allergies, daily_calories_target, weekly_budget)`
    *   **Purpose:** Commits any changes made in the Streamlit sidebar directly to the local database, allowing user preferences to persist across sessions.

### Meal Calendar Helpers
*   `clear_meal_plan()`
    *   **Purpose:** Deletes all entries from the `meals` table to prepare for a new meal plan generation.
*   `save_meal_plan(meals_list)`
    *   **Purpose:** Batch-inserts a generated 21-meal menu (3 meals per day, Monday–Sunday) into the database.
*   `get_all_meals()`
    *   **Purpose:** Queries the database for the active week's meal plan to display on the calendar tabs.
*   `update_meal_status(meal_id, is_eaten)`
    *   **Purpose:** Updates the consumption status of a meal. Tracks whether a user consumed a planned meal (enabling future tracking metrics).

### Grocery & Inventory Helpers
*   `clear_grocery_list()`
    *   **Purpose:** Purges the proposed grocery items so a new budget proposal can be computed.
*   `save_grocery_list(items_list)`
    *   **Purpose:** Takes the proposed item names and their estimated market values generated by the AI and saves them to the database.
*   `get_grocery_list()`
    *   **Purpose:** Retrieves all proposed grocery list items and their costs to render the interactive shopping checklist.
*   `update_grocery_item_status(item_id, is_bought)`
    *   **Purpose:** Tracks whether a user actually purchased an item, instantly triggering UI updates and state recalculations.
*   `get_bought_groceries()`
    *   **Purpose:** **(Crucial State Link)** Queries the database to retrieve a list of string item names where `is_bought = 1`. This exact inventory list is passed to the LLM in Phase 3.

### System Maintenance
*   `reset_all_data()`
    *   **Purpose:** Clears both `meals` and `grocery_list` records completely, returning the user to the starting state of Phase 1.

## 2. Prompt & Integration Engine (`llm.py`)
This module manages communication with the OpenAI API, implementing structured JSON outputs to enforce schema constraints.

*   `generate_grocery_list_proposal(profile)`
    *   **Input:** The user profile dictionary (diet, allergies, target calories, weekly budget).
    *   **LLM Behavior:** Directs `gpt-4o-mini` to act as a financial grocery planner. It translates calorie requirements into real-world package units (e.g., "1 carton of eggs (12)" rather than individual eggs) and estimates standard market pricing.
    *   **Constraint Enforcement:** Uses OpenAI's structured JSON response format to return a list matching the exact table schema required by `database.py`. The LLM is strictly prompted to ensure the cumulative cost of the items remains below the user's budget ceiling.
*   `generate_meals_from_groceries(profile, bought_groceries)`
    *   **Input:** The user profile dictionary and an array of strings representing only the checked-off, purchased ingredients.
    *   **LLM Behavior:** Directs the model to act as a resource-constrained chef. It generates a 21-meal schedule using strictly the items present in the `bought_groceries` array, assuming the presence of basic pantry staples (water, oil, salt, pepper).
    *   **Constraint Enforcement:** Restricts ingredients on a zero-trust model, ensuring the AI does not generate dishes requiring components the user did not actually buy.

## 3. Orchestration & User Interface (`app.py`)
The Streamlit frontend serves as the state controller, handling conditional rendering based on database conditions.

### Major UI Components
*   **Sidebar Configuration Form:** Constantly loaded on the left side, enabling real-time edits to the target budget, daily calorie goals, allergies, and diet types.
*   **Sequential Stage Gateways:**
    *   *Gateway 1 (Empty Database):* Displays only Phase 1 with a prompt to generate a grocery list.
    *   *Gateway 2 (Groceries Exist, No Meals):* Displays the interactive grocery list with real-time budget tracking. Shows a warning if the current selected cart exceeds the budget. Displays a disabled generation button until at least one ingredient is purchased.
    *   *Gateway 3 (Meals Exist):* Displays the interactive calendar alongside the grocery checklist below it for continuous reference.

## How This Project Proves Engineering Competence
If asked about this project in an interview, you can highlight these specific points:
1.  **Deterministic AI Output:** You controlled unstructured text models to return precise JSON schemas, directly parseable by SQLite without manual string manipulation.
2.  **Constraint-Based Generation:** You solved the "hallucination" and "idealized planning" issues common in AI tools. Instead of letting the AI suggest arbitrary ingredients, the AI's recipe generator is strictly bound to a local SQLite inventory table.
3.  **State Persistence:** You decoupled frontend UI changes from server processes by writing clean DB-wrapper states, ensuring user selections survive system refreshes.
